---

# 2. System Overview

The Alert Intelligence Engine is a modular batch-processing pipeline that ingests disaster alerts from multiple heterogeneous formats, extracts structured information, normalizes the extracted data into a common schema, validates the normalized records, detects duplicate alerts, and exports a standardized JSON file.

The system is intentionally designed as a processing engine rather than a web application.

# 6. Core Data Models

## 6.1 ParsedAlert

Intermediate object produced by every parser.

Purpose:

- Hold raw extracted values
- Remain independent of final schema
- Allow shared normalization logic

Typical fields:

- raw hazard
- raw severity
- raw urgency
- raw certainty
- raw location
- raw timestamps
- raw action
- source metadata

No normalization is performed here.

---

## 6.2 NormalizedAlert

Final object that exactly matches:

expected_normalized_schema.json

No extra fields are permitted.

Every output record written to normalized_alerts.json must conform to this model.

---

# 7. Parser Architecture

## BaseParser

Abstract interface implemented by every parser.

Responsibilities:

- Accept raw input
- Parse source-specific structure
- Return ParsedAlert

No normalization.

No validation.

No duplicate detection.

---

## JSON Parser

Responsibilities:

- Parse JSON
- Extract raw fields

Output:

ParsedAlert

---

## CAP XML Parser

Responsibilities:

- Parse CAP XML
- Extract raw fields

Output:

ParsedAlert

---

## RSS Parser

Responsibilities:

- Parse RSS XML
- Extract raw fields

Output:

ParsedAlert

---

## Plaintext Parser

Responsibilities:

- Perform deterministic regex extraction
- Return ParsedAlert

Gemini is NOT called directly inside the parser.

The parser only extracts what can be reliably identified.

# 8. Pipeline Design

Processing sequence:

```
Input File

↓

Format Detection

↓

Parser Router

↓

Source Parser

↓

ParsedAlert

↓

Structural Validation

↓

Normalization Engine

↓

Gemini Fallback (Plaintext Only)

↓

Final Schema Validation

↓

Batch Deduplication

↓

normalized_alerts.json
```

The pipeline processes alerts individually until deduplication.

Deduplication operates on the complete normalized batch.

---

# 9. Validation Strategy

## Stage 1 — Structural Validation

Purpose:

Validate parser output before normalization.

Checks:

- Parser succeeded
- Minimum usable fields exist
- Record is structurally recoverable

Malformed records are skipped with warnings.

---

## Stage 2 — Final Schema Validation

Uses Pydantic.

Checks:

- Required fields
- Enum values
- Datatypes
- ISO-8601 timestamps

Only validated records proceed.

---

# 10. Normalization Engine

The Normalization Engine is responsible for converting ParsedAlert into NormalizedAlert.

Internally it consists of:

## Severity Mapper

Uses:

severity_mapping_reference.csv

Unknown values:

Unknown

Adds parse warning.

---

## Urgency Mapper

Maps urgency values according to provided references.

Unknown values become:

Unknown

---

## Certainty Mapper

Maps certainty values according to provided references.

Unknown values become:

Unknown

---

## Location Mapper

Uses:

location_reference.csv

Unknown locations:

location_id = null

Adds parse warning.

# 11. Gemini Integration Strategy

Gemini is a fallback enrichment module.

It is never the primary parser.

It is used only when deterministic extraction fails to populate the minimum expected fields from plaintext alerts.

Workflow:

```
Regex Extraction

↓

Required Fields Present?

↓

YES

↓

Continue

↓

NO

↓

Gemini Extraction

↓

Merge Missing Fields

↓

Continue
```

Gemini is never used for:

- JSON
- CAP XML
- RSS XML

---

# 12. Deduplication Strategy

Deduplication executes only after every record has been normalized.

Duplicate score:

| Component | Weight |
|-----------|-------:|
| Hazard Match | 35% |
| Location Match | 30% |
| Time Window Overlap | 20% |
| Text Similarity | 15% |

Threshold:

0.75

The first matching record is treated as canonical.

Subsequent matches are marked:

is_duplicate = true

Records are never deleted.

---

# 13. Parse Warning Policy

| Situation | Action |
|-----------|--------|
| Missing optional field | Add warning |
| Unknown severity | Normalize to Unknown + warning |
| Unknown urgency | Normalize to Unknown + warning |
| Unknown certainty | Normalize to Unknown + warning |
| Unknown location | location_id = null + warning |
| Gemini API failure | Warning + continue |
| Invalid enum | Normalize + warning |
| Broken XML | Skip record |
| Broken JSON | Skip record |
| One malformed record | Continue processing remaining records |

The batch must never terminate because of one malformed record.

---

# 14. Error Handling Strategy

Each record is processed independently.

```
For each record

↓

Try

↓

Success

↓

Normalize

↓

Validate

↓

Output

↓

Exception

↓

Log Warning

↓

Continue
```

Failures never stop batch execution.

# 20. Technical Completion Criteria

The implementation is considered complete when:

- All four parsers successfully process the provided datasets.
- ParsedAlert objects are generated correctly.
- Normalization is completed using the provided reference mappings.
- Gemini fallback successfully enriches incomplete plaintext alerts.
- Final records conform exactly to expected_normalized_schema.json.
- Duplicate alerts are identified correctly.
- Parse warnings are generated where appropriate.
- normalized_alerts.json is generated successfully.
- All automated tests pass.
- Logging is implemented consistently.
- Documentation is complete.
